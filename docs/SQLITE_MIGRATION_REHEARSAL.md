# AttendanceSystem v1.0.0-rc.6 — isolated SQLite migration and rollback rehearsal

**Status: engineering evidence only, production NO-GO.** The public SQLite migration API remains disabled for existing old databases, even if a caller sets \`allowExistingUpgrade:true\`. This version does not connect scanners, export student records, send notifications, create an institutional migration service, or approve real private-data processing.

## Delivered in code

- New \`SyntheticMigrationRehearsal.Run(sourcePath, oldProviderSha256)\` is **internal** and reachable only from existing \`--self-test-legacy-compat\` test logic. It requires the previous \`SyntheticMigrationScope.Demand\` checks (explicit CI test marker, existing file immediately under generated OS TEMP fixture folder, no symlinks/junctions), an exactly named old-provider test fixture, maximum **4 MiB**, a matching receipt SHA-256 *before SQLite is opened*, and the previously implemented fail-closed schema preflight for version 0 or 1.
- It verifies that the source has **4 named-only fake test records in Students, 3 Attendance and 2 Holidays**, including a strict synthetic fixture-ID marker; unknown or actual institutional record layouts are rejected.
- The source is **never passed to the migration function**. The code obtains a **consistent SQLite online backup clone**, not a WAL-unsafe \`File.Copy\`. It verifies that the clone's original schema and full canonical digest of every historical column match the source.
- \`InitializeSyntheticFixtureAtPath(clone)\` performs the schema-v4 upgrade **on the clone only**, creating the same pre-migration SQLite backup as the existing synthetic migration process. The rehearsal checks exact legacy-row preservation, SQLite integrity and FK status after upgrade, and validates the backup retained the old schema and its source rows.
- A **separate rollback DB** is restored with SQLite's online backup API from the pre-migration backup. Its old schema and exact row content are checked. Finally, the original source fixture is reopened and compared again; it must still have its old version and unchanged source data.
- Any exception or successful completion triggers cleanup of clone, rollback and clone-only backup files, including SQLite WAL/SHM sidecars. This cleanup is for **fake test data only**; deletion of a private plaintext file is *not secure erasure*.

The \`MigrationRehearsalReceipt\` contains only generated schema numbers, totals and safe Boolean states (clone-only, source unchanged, backup verified, rollback verified, realDataUsed=false, productionMigrationAuthorized=false, decision=NO-GO). No student keys, names, phones, event contents, SQLite file paths, personally derived hashes or secret keys can escape the rehearsal result.

## CI review evidence

The existing **Windows .NET 10** cross-provider test now runs the rehearsal on both real files generated by the isolated old **System.Data.SQLite.Core 1.0.119** process and reopened with **System.Data.SQLite 2.0.4 + SourceGear.sqlite3 3.53.4**. It rejects an incorrect SHA-256 source receipt **before** creating any clone and verifies no temporary plaintext artifacts remain after a valid rehearsal.

Only after both exact source files pass does the CI optionally generate a **synthetic-only, unsigned** JSON evidence report:

- \`migration-rehearsal.json\`: 2 numeric/boolean receipts with explicit NO-GO, no private fields or source paths, pinned provider-version labels and known limitations.
- \`SHA256SUMS.txt\`: checksum of that report, not a code signature, attestation or owner's authorization.

The output folder is restricted to a fresh \`attendance-rc6-migration-evidence\` immediate child of the operating system's TEMP directory. The workflow checks format, NO-GO, two cases and checksum before copying only these two tiny non-PII files to a **7-day GitHub Actions artifact**. The generated SQLite data and plaintext backups are explicitly excluded from artifacts and deleted in a finally block.

## What this does and does not prove

| Question | Rehearsal assertion | Production interpretation |
| --- | --- | --- |
| Does v2 read a file written by v1? | Tested for two old-provider-generated fake 0/1 layouts | Does not prove all historical institution layouts |
| Does the source change? | Full column-by-column canonical digest before and after | Synthetic sources only; no approved real files processed |
| Does migration preserve source rows? | Clone must match source after schema-v4 update | This is a regression contract, not an operator signoff |
| Is pre-migration backup complete? | Reopens with old version, exact legacy-row digest | No secure production key custody/offsite backup |
| Is rollback viable? | Separate SQLite database restored and read at original version | Not an OS power-cut test or a real RTO/RPO drill |
| Can user pass public upgrade flag? | rc.5 public gate remains unconditional deny | No authorized real-data upgrade worker exists |
| Are approvals present? | \`ProductionMigrationAuthorized=false\`, \`NO-GO\` unconditionally | Product, security, privacy and operations must approve externally |

**Remaining hard blockers:** historical public attendance.db privacy review; data-controller-approved genuinely de-identified representative fixture; encrypted scratch/temp with audited OS ACL, KMS and offsite backup; independent Realand hardware/SDK provenance and vendor ACK; organization OIDC/scoped permissions, guardian rights/consent, safe outbound provider; 14-day actual pilot and signed release decisions. The existing original-schema migration can produce **plaintext** backups, therefore it must never be used for actual student data until a separate secure, approved implementation exists.

**No main merge, v1.0.0 tag, student-data migration or production deployment is authorized by this change.** Tracking: [PR #30](https://github.com/MeiRR17/AttendanceSystem/pull/30), Issue #14, Issue #3 and docs/RELEASE_READINESS.md.
